Lecture 4

Data Cleaning

Missing data is the most common data-quality problem you'll meet, and there is no single correct way to handle it. This lecture covers the options — drop, replace, impute, flag — and closes with a worked example of spotting problems row by row.

Introduction to missing data

Missing data refers to values that are not recorded, unavailable, or absent for one or more variables in a dataset. It reduces data quality and can affect the accuracy of any analysis or machine-learning model built on top of it. It can come from data-entry errors, unanswered survey questions, system failures, or information that simply wasn't available.

During exploration, missing values should be identified. During preparation, they can be handled by removing affected rows/columns, replacing values through imputation, or keeping them as-is when the absence itself is meaningful.

Introduction to data cleaning

Data cleaning is an essential stage of data preparation: before analysing a dataset, you need to check whether it's complete, valid, consistent and suitable for analysis. Four closely related areas make up the work:

  • Data cleaning
  • Documenting the cleaning process
  • Handling missing data
  • Dropping, imputation and flagging

The underlying idea is simple: the quality of the analysis depends heavily on the quality of the data fed into it.

Purpose of data cleaning

Raw data is rarely ready for immediate analysis — it may contain missing values, duplicate records, inconsistent labels, incorrect data types, obsolete fields or unusual values. The purpose of cleaning is to minimise the effect of poor-quality inputs on the final analysis — commonly summed up as Garbage In → Garbage Out.

Example

A supermarket dataset contains customer ages, product prices and transaction values. If ages contain text, prices contain negative numbers, and customer information is incomplete, any analysis built on it may become misleading.

What cleaning involves

Data cleaning means examining the dataset for errors and deciding how each one should be treated. A value can be technically stored in the database and still be wrong — a postal code like 06269 becomes 6269 when it's stored in a numeric field and loses its leading zero. Cleaning means asking, for every field:

  • Is this value valid?
  • Is the data type correct?
  • Does this value make sense?
  • Is information missing?

Documenting the cleaning process

Cleaning should be documented so another person can understand what was changed and why. A good cleaning record explains:

  • What problem was identified
  • Which variable or records were affected
  • What action was taken
Example log entry

"Three missing age values were replaced using the median age because the distribution was skewed."

Documentation improves transparency, reproducibility and accountability. The recommended loop: Raw Data → Cleaning Steps → Clean Dataset → Cleaning Log.

Should we drop missing data?

One option is to delete rows with missing values (df = df.dropna()), but it's riskier than it looks: you lose every other field in that row too, and the pattern of missingness may be systematic rather than random, not just unlucky noise.

If Customer B is dropped for a missing Age, their €51,000 Income is lost too. Does deleting the record create more damage than keeping it?

Replacing with a constant

A simpler alternative: replace missing values with a fixed value chosen by the analyst — 0.0 for a numeric field, or a label like "Missing" / "Unknown" for a categorical one.

Caution

A constant must not accidentally imply real meaning. Replacing a missing Age with 0 could suggest a newborn customer — a separate "Missing" category is safer whenever the distinction matters.

Imputation: mean, median, mode

Imputation replaces a missing value with a reasonable estimate: the mode for categorical data, the mean or median for numerical data.

Example

Cubic-inches: 350, missing, 302, 400, 89 — Mean = 285.25.

Sorted non-missing values: 89, 302, 350, 400 — Median = 326.

The missing brand value is imputed with the mode, US; the missing cubic-inch value with the mean, 200.65.

Imputation keeps the record in the dataset — but the replacement value is an estimate, not an original observation.

Limitations of mean/mode imputation

The mean isn't always a good "typical" value, and replacing many observations with the same number artificially reduces variation — which can make statistical confidence look stronger than it really is. If salary data is skewed by a handful of very high earners, the mean will sit well above what a typical employee earns; the median is usually the safer replacement in that case.

Main principle: choose the imputation method according to the variable and its distribution.

Flagging missing or imputed values

A useful technique is adding an extra column that records whether the original value was missing — preserving that information even after imputation fills the gap.

AgeAge_Missing
250
311
380

Here, 31 is an imputed value, and Age_Missing = 1 tells us the original observation was unavailable. This matters because missingness itself can be meaningful — customers who don't share income information may behave differently from those who do.

Good practice

Impute the value when appropriate, but keep a record that it was originally missing.

Choosing the appropriate strategy

There is no single correct solution for every missing-data problem:

  • Dropping may be fine when only a very small number of observations are affected and removing them is unlikely to introduce bias.
  • Imputation is preferable when keeping the observation matters, as long as the method fits the variable and its distribution.
  • Flagging is useful whenever the fact a value was missing could itself be informative.

More advanced imputation methods estimate missing values using interpolation, regression, classification trees or regression trees, based on neighbouring values or relationships with other attributes in the dataset.

The final cleaning principle, as a loop: Inspect → Understand → Clean → Document → Validate (and back to Inspect).

Take this small customer table and look for problems field by field.

Zip

Don't assume a local format — 90210 is a US zip code, J2S7K7 is a Canadian postal code, and in a dataset drawing from multiple countries that's expected, not an error. Watch for data-type conversion issues too: zip code 06269 stored in a numeric field truncates its leading zero and becomes 6269 (the real zip code for Storrs, CT) — row 1004's value is exactly that artefact, not a different place.

Gender

Customer 1003's Gender value is simply missing.

Income

  • €10,000,000 (customer 1003) — plausible for the Beverly Hills zip code 90210, but still an outlier that can skew statistical and data-mining methods.
  • −€40,000 (customer 1002) — income below zero is out of bounds; most likely a data-entry error worth raising with the database administrator.
  • €99,999 (customer 1005) — may be valid, but every other value is rounded to the nearest €5,000, and legacy systems sometimes use a value like this as a database code for "missing."

Also confirm the unit of measure throughout — is the Canadian customer's income recorded in Canadian dollars, or converted?

Age

  • "C" (customer 1001) — possibly a leftover from an earlier age-bin categorisation. A data-mining tool will likely reject a text value in an otherwise numeric field, so this needs resolving before analysis.
  • 0 (customer 1004) — a newborn making a €1,000 transaction is implausible; far more likely this is a missing value or other anomaly coded as zero.

Age values go stale over time. It's usually better to store a date field (like date of birth) and calculate age as needed, rather than storing age itself.

Marital status

What does each code actually mean? Don't assume — is S for "Single" or "Separated"? Codes can also come from another language entirely: in some systems C means "Cold" in English, but "Chaud" (Hot) in French.

Transaction amount

These values look fine, assuming a common unit of measure across all rows.
